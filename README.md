### 1. 서버가 매번 다른 곳에서 죽었다

```
증상   클라를 여러 개 붙이고 접속/종료를 반복하면 크래시. 죽는 위치가 매번 다름
가설   소켓 문제 → recv/send 반환값과 WSAGetLastError 전수 확인 → 전부 정상 ❌
전환   죽는 '순간'이 아니라 죽기 '직전'의 흐름을 기록해 비교
발견   공통점: 항상 누군가 접속을 끊은 직후
원인   수신 처리 도중 끊긴 세션을 그 자리에서 delete + erase
       → 그 목록은 바로 그 순간 순회 중 → 반복자 무효화
해결   지연 삭제 — 플래그만 내리고, 다음 루프 최상단에서 일괄 정리
```
→ [`Server.cpp:125`](./01_TCPFighter_Server/Server/Server.cpp#L125) · [`Session.cpp:119`](./01_TCPFighter_Server/Server/Session.cpp#L119)

**왜 지연 삭제인가** — 순회 중 `erase`의 반환 반복자를 받는 방법도 있지만, 끊김은 순회하는 그 자리에서만 생기지 않습니다. 브로드캐스트 도중 다른 세션의 송신 실패, 공격 판정 중 HP 0 등 **목록을 순회하는 쪽이 모르는 깊은 호출에서** 끊김이 결정됩니다. 그래서 "끊김 결정"과 "삭제"를 분리해, 삭제는 아무도 순회하지 않는 루프 최상단 한 곳에서만 하도록 했습니다.

**같은 버그를 또 만났다** — 이후 강의를 따라 만든 IOCP 서버에서 브로드캐스트 중 크래시가 났고, AI는 락 문제로 보고 뮤텍스를 제안했습니다. 원인은 락과 무관한 **같은 순회 중 삭제**였습니다. 한 번 직접 겪어 봤기 때문에 AI의 답이 틀렸다는 걸 알아챌 수 있었습니다.

### 2. 접속자가 0명인데 CPU 코어 하나를 다 쓰고 있었다

처음엔 모든 세션을 `WriteSet`에 상시 등록하고 있었습니다. 소켓은 거의 항상 "쓰기 가능"이라 `select()`가 매번 즉시 리턴합니다. **송신 큐에 데이터가 있는 세션만 등록**하도록 고쳤고, 해결됐다고 생각했습니다.

그런데 접속자 0명 상태에서 프로세스 CPU 시간을 재 보니:

| | 5초 동안 사용한 CPU 시간 |
|---|---|
| WriteSet만 고친 상태 | **4.84초** (코어 1개 100%) |
| 타임아웃 수정 후 | **0.17초** (63명 접속 시에도 4초 중 0.19초) |

원인은 `select` 타임아웃 `{0, 0}`. 기다릴 이벤트가 없어도 즉시 리턴하고, 메인 루프에 대기가 없으니 쉬지 않고 돕니다. 1ms로 바꿔 이벤트가 없으면 잠깐 잠들게 했습니다.

```cpp
// 0 으로 두면 이벤트가 없어도 즉시 리턴해 루프가 CPU 를 다 쓴다
timeout.tv_usec = 1000;
```
→ [`Server.cpp:148`](./01_TCPFighter_Server/Server/Server.cpp#L148) (WriteSet 조건부 등록) · [`Server.cpp:155`](./01_TCPFighter_Server/Server/Server.cpp#L155)

**왜 1ms인가** — 게임 로직은 20ms(50fps) 프레임이라 네트워크는 그보다 훨씬 자주 확인해야 합니다. 1ms면 응답 지연은 프레임 대비 무시할 수준이면서 유휴 CPU는 거의 0이 됩니다. 다음 프레임까지 남은 시간을 타임아웃으로 주는 방법도 있지만, 측정상 1ms로 충분해 단순한 쪽을 택했습니다.

**배운 것** — "고쳤다"는 느낌이 아니라 숫자로 확인해야 한다. 첫 번째 수정은 맞는 수정이었지만 원인의 전부가 아니었다.

### 3. 39번째 접속자부터 화면이 깨졌다

더미 클라이언트로 접속 수를 늘려 가며 측정했습니다. 각 클라가 받은 바이트를 `[code][size][type]` 단위로 잘라, 코드가 `0x89`가 아니면 스트림이 깨진 것으로 셌습니다.

| 접속 수 | 입장 시 스트림이 깨진 클라 | 이동 브로드캐스트 도달률 |
|---|---|---|
| 38 | 0 | 100% |
| 40 | **1** | 100% |
| 50 | **11** | 100% |
| 63 | **24** | **74%** |

**정확히 39번째부터** 깨지기 시작했다는 게 단서였습니다.

```
새 접속자는 기존 인원 전원의 캐릭터 정보를 한 번에 받는다 (패킷당 13바이트)
  13 × 39 = 507바이트  >  송신 링버퍼 500바이트
링버퍼 Enqueue는 공간이 부족하면 들어가는 만큼만 넣고, SendPacket은 반환값을 보지 않았다
  → 패킷 중간이 잘린 채 전송 → 그 뒤 모든 패킷의 경계가 어긋남
```

TCP는 바이트 스트림이라 **한 바이트만 빠져도 이후 전체가 깨집니다.** 버퍼를 키우는 것만으로는 언젠가 같은 일이 생기므로, 다 못 넣으면 잘라 넣지 않고 세션을 끊도록 했습니다.

```cpp
//패킷이 잘린 채로 들어가면 이후 스트림 전체가 어긋나므로, 다 못 넣으면 끊는다
if (m_sendQ.GetFreeSize() < size)
{
    printf("ID: %d, SendQ is full!\n", m_sessionID);
    Disconnect();
    return;
}
```
→ [`Session.cpp:109`](./01_TCPFighter_Server/Server/Session.cpp#L109) · 송신 버퍼 500 → 10000바이트 [`GameDefine.h:41`](./01_TCPFighter_Server/Server/GameDefine.h#L41)

| 접속 수 | 수정 전 깨짐 / 도달률 | 수정 후 깨짐 / 도달률 |
|---|---|---|
| 50 | 11 / 100% | 0 / 100% |
| 63 | 24 / 74% | **0 / 100%** |

### 4. 64번째 접속자는 아무 반응이 없었다

`accept`는 성공하는데 그 세션의 패킷은 영영 처리되지 않았습니다. Windows의 `FD_SET`은 `fd_set`이 64칸(`FD_SETSIZE`)으로 차 있으면 **에러 없이 무시**합니다. listen 소켓이 1칸을 쓰므로 63명을 넘는 세션은 `select` 대상에서 빠집니다.

연결은 됐는데 아무 일도 안 일어나는 상태가 가장 나쁘다고 판단해, 정원을 넘으면 **명시적으로 접속을 거절**하도록 했습니다.

```cpp
// fd_set 이 꽉 차면 FD_SET 이 조용히 무시해 그 세션은 영영 recv 되지 않는다
if (m_sessions.size() >= MAX_SESSION)
{
    printf("Session Full # IP:%s\n", clientIP);
    closesocket(clientSocket);
    return;
}
```
→ [`Server.cpp:214`](./01_TCPFighter_Server/Server/Server.cpp#L214)

수정 후 100명 접속 시: 63명 정상 처리, 37명 거절, 브로드캐스트 100%.

**다음 단계** — `select` 한 번에 63명이 구조적 한계. 이 한계를 넘기 위해 IOCP를 공부했습니다.

### 5. "좌표를 검증한다"고 써 놓은 코드는 반대로 동작했다

클라가 보고한 좌표가 서버 좌표와 ±50 이상 차이 나면 무시한다 — 고 설명에 적었습니다. 설명과 코드를 대조하다가 **조건이 반대로** 되어 있다는 걸 발견했습니다. 오차를 *벗어날 때* 클라 좌표를 받아들이고 있었습니다.

```cpp
// 수정 전 — 순간이동 좌표를 그대로 받아들임
if (abs(pSession->x - pRecvPacket->x) > dfERROR_RANGE || ...)
{
    pSession->x = pRecvPacket->x;
    pSession->y = pRecvPacket->y;
}
```
```cpp
// 수정 후 — 오차를 벗어나면 로그만 남기고 거부
if (abs(m_x - x) > dfERROR_RANGE || abs(m_y - y) > dfERROR_RANGE)
{
    printf("# PositionError # ...");
    return;
}
```
→ [`Session.cpp:317`](./01_TCPFighter_Server/Server/Session.cpp#L317)

**거부한 뒤에는?** — 다른 클라에게 브로드캐스트하는 좌표는 클라가 보낸 값이 아니라 **서버 좌표**(`m_x`, `m_y`)라서, 위조 좌표가 다른 플레이어 화면으로 퍼지지 않습니다. 다만 위조한 본인 클라의 화면을 서버 좌표로 되돌리는 동기화 패킷은 아직 없습니다 — 다음에 붙일 부분입니다.

**배운 것** — 검증이 *있다고 믿는 것*과 *실제로 동작하는 것*은 다르다. 클라가 판정에 관여하는 순간 그건 치팅 통로가 된다.

### 링버퍼는 서버에 올리기 전에 정답 모델과 대조했다

수신·송신이 모두 링버퍼를 거치므로, 경계 처리가 틀리면 패킷이 깨져도 원인이 서버 로직처럼 보입니다. 그래서 서버에 붙이기 전에 따로 검증했습니다. 3번 문제 때 링버퍼 내부를 의심하지 않고 바로 *사용하는 쪽*을 볼 수 있었던 이유입니다.
→ [`ringbuffer_test/main.cpp`](./01_TCPFighter_Server/ringbuffer_test/main.cpp)
- `std::string`을 **정답 모델**로 두고, Enqueue / Dequeue / Peek를 무작위로 **회당 1만~5만 번** 실행
- 매 연산마다 반환 바이트 수 · 실제 데이터 · UseSize · FreeSize를 정답 모델과 대조

### 그 외 설계
- **링버퍼 무복사 수신** — 끊김 없이 쓸 수 있는 공간의 포인터를 `recv()`에 직접 전달
- **TCP 프레이밍** — Header Peek → 길이 확인 → Dequeue. 패킷 코드(`0x89`)가 다르면 세션 종료
- **부분 전송** — `send()`가 보낸 만큼만 큐에서 제거, `WSAEWOULDBLOCK`은 정상 분기

### 측정 방법
- 서버를 로컬에서 실행 → `python load_test/dummy_client.py <N>`
- 0.02초 간격으로 N명 접속 → 2초 대기 후 각자 받은 패킷 검사 → 전원 이동 패킷 1회 전송 → 2초 대기 후 도달 수 집계
- CPU: 프로세스 `TotalProcessorTime`을 일정 간격으로 두 번 읽어 차이 계산

## AI는 이렇게 썼습니다

**기준** — 배울 때는 코드를 받지 않고, 결과물을 다듬을 때는 맡긴다. 맡긴 결과는 직접 해 본 경험으로 검증한다.

- 학습: 설계를 먼저 말하고 검토받는다. 완성 코드는 받지 않는다.
- 다듬기: 단일 파일(990줄)이던 TCPFighter를 `Server` / `Session` / `App`으로 나누는 작업은 맡기고, 원본과 동작을 대조했다.
